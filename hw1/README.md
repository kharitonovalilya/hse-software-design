## Возможности

Приложение позволяет:

- добавлять транспорт в парк после технического осмотра;
- учитывать оборудование на балансе;
- автоматически выдавать инвентарные номера новым объектам;
- получать количество объектов в парке;
- рассчитывать суммарное суточное энергопотребление;
- получать список транспорта, подходящего для новичков;
- выводить названия и инвентарные номера всего инвентаря;
- запускать демонстрационный сценарий;
- работать с приложением через интерактивное консольное меню.

## Предметная модель

Все объекты, которые находятся на балансе, реализуют интерфейс
`InventoryItem`.

```text
InventoryItem
├── Transport
│   ├── Bike
│   ├── Scooter
│   └── ElectricBike
└── Equipment
    ├── Helmet
    └── ChargingStation
```

`Transport` содержит общие характеристики транспорта:

- автоматически сгенерированный инвентарный номер;
- название;
- показатель простоты использования для новичка от 1 до 10;
- состояние тормозов;
- состояние шин в процентах.

Транспорт считается подходящим для новичка при значении
`friendlyForBeginner >= 6`.

Инвентарные номера пользователь не вводит. При создании нового
`Transport` или `Equipment` номер выдаётся через общий
`InventoryNumberGenerator`, поэтому транспорт и оборудование используют
одну последовательность номеров.

### EnergyConsumer

`EnergyConsumer` реализуют объекты, потребляющие энергию:

- Scooter
- ElectricBike
- ChargingStation

В рамках модели проекта для таких объектов хранятся:

- суточное энергопотребление;
- текущий процент заряда батареи.

## Технический осмотр

Техосмотр описан интерфейсом:

```java
public interface ServiceCenter {
    boolean inspect(Transport transport);
}
```

В условии задания конкретные правила техосмотра не определены, поэтому
в проекте добавлены простые технические критерии:

- тормоза должны быть исправны;
- состояние шин должно быть не ниже 60%;
- для энергопотребляющего транспорта заряд батареи должен быть не ниже 20%.

Если хотя бы одно обязательное условие не выполнено, транспорт не
принимается в парк.

## Архитектура

### RentalPark

`RentalPark` отвечает только за хранение состояния парка.

Все объекты хранятся в одной коллекции:

```java
List<InventoryItem>
```

Из неё можно получить транспорт и объекты, реализующие
`EnergyConsumer`.

### RentalParkService

`RentalParkService` содержит основные сценарии приложения:

- приём транспорта после техосмотра;
- добавление оборудования;
- получение всего инвентаря и его количества;
- расчёт суммарного энергопотребления;
- получение транспорта для новичков.

При добавлении транспорта сервис не проверяет технические параметры
самостоятельно, а вызывает внедрённый `ServiceCenter`.

### ConsoleApplication

`ConsoleApplication` отвечает за ввод и вывод.

Пользователь вводит характеристики объекта, например состояние тормозов,
шин и батареи. Консоль не решает, пройдёт ли транспорт техосмотр — она
передаёт созданный объект в `RentalParkService`, а решение принимает
`ServiceCenter`.

## Dependency Injection

Для DI-контейнера используется Spring Framework.

`RentalParkService` зависит от абстракции `ServiceCenter`:

```java
public RentalParkService(
        RentalPark rentalPark,
        ServiceCenter serviceCenter
) {
    this.rentalPark = rentalPark;
    this.serviceCenter = serviceCenter;
}
```

В обычном запуске Spring подставляет `DefaultServiceCenter`.
В unit-тестах вместо него передается `FakeServiceCenter`.

Это позволяет отдельно проверить:

1. правила настоящего технического осмотра;
2. реакцию `RentalParkService` на результат техосмотра.

## Использование SOLID

### S — Single Responsibility Principle

- `RentalPark` хранит состояние парка;
- `RentalParkService` реализует бизнес-сценарии;
- `DefaultServiceCenter` выполняет техосмотр;
- `ConsoleApplication` отвечает за взаимодействие с пользователем;
- `InventoryNumberGenerator` выдаёт инвентарные номера.

У всех классов одна область ответственности. Например, изменение критериев техосмотра не требует изменения
консольного интерфейса или `RentalPark`.

### O — Open/Closed Principle

Новый вид транспорта можно добавить наследованием от `Transport`.
Если он потребляет энергию, он дополнительно реализует
`EnergyConsumer`.

Основная логика `RentalPark` и `RentalParkService` при этом не меняется.
Если новый тип должен создаваться пользователем через меню, потребуется
добавить соответствующий вариант в `ConsoleApplication`. Это сознательная
граница текущего решения.

### L — Liskov Substitution Principle

`Bike`, `Scooter` и `ElectricBike` могут использоваться в местах, где
ожидается `Transport`, не изменяя контракт базового класса.

То же относится к `Helmet` и `ChargingStation` относительно
`Equipment` и `InventoryItem`.

### I — Interface Segregation Principle

В проекте используются небольшие интерфейсы с разными обязанностями:

- `InventoryItem` — объект на балансе;
- `EnergyConsumer` — объект с энергетическими характеристиками;
- `ServiceCenter` — контракт технического осмотра транспорта.

Например, обычный `Bike` не обязан реализовывать методы
энергопотребления.

### D — Dependency Inversion Principle

`RentalParkService` зависит от интерфейса `ServiceCenter`, а не от
`DefaultServiceCenter`.

Благодаря constructor injection production-реализация предоставляется
Spring-контейнером, а в unit-тестах техосмотр легко заменяется.

## Тестирование

Используются JUnit 5. Тесты разделены по ответственности.

### DefaultServiceCenterTest

Проверяет реальные правила техосмотра:

- исправный транспорт с допустимым состоянием шин принимается;
- транспорт со сломанными тормозами отклоняется;
- транспорт с изношенными шинами отклоняется;
- энергопотребляющий транспорт с зарядом ниже 20% отклоняется;
- значение ровно 20% проходит граничную проверку.

### RentalParkServiceTest

Проверяет бизнес-сценарии `RentalParkService`.

Вместо настоящего `DefaultServiceCenter` используется простой
`FakeServiceCenter`. В каждом тесте ему заранее задаётся результат
техосмотра: принять или отклонить транспорт.

Проверяются:

- добавление транспорта, когда `ServiceCenter` его принимает;
- отказ в добавлении транспорта, когда `ServiceCenter` его отклоняет;
- расчёт суммарного суточного энергопотребления;
- получение только транспорта, подходящего для новичков;
- получение всего инвентаря;
- правильный подсчёт количества объектов в парке.

### RentalParkTest

Проверяет выборки из общего хранилища:

- получение только транспорта;
- получение объектов `EnergyConsumer` из разных веток иерархии.

### TransportTest

Проверяет основные правила самого `Transport`:

- значение `friendlyForBeginner = 6` считается подходящим для новичка;
- значение `friendlyForBeginner = 5` не считается подходящим;
- значения `friendlyForBeginner` меньше 1 и больше 10 отклоняются;
- состояние шин меньше 0 и больше 100 отклоняется.

### InventoryNumberGenerationTest

Проверяет, что разные типы инвентаря получают инвентарные номера
из одной общей последовательности и номера не совпадают.

### ConsoleApplicationTest

Проверяет только базовые пользовательские сценарии консоли:

- добавление велосипеда через консоль;
- добавление шлема через консоль;
- вывод основных отчётов об инвентаре, количестве объектов,
  энергопотреблении и транспорте для новичков.

## Демонстрационный сценарий

При старте программа предлагает запустить demo.

В нём создаются все текущие виды объектов и показываются:

- добавление оборудования;
- автоматическая выдача инвентарных номеров;
- успешный техосмотр;
- отказ из-за плохого технического состояния;
- вывод инвентаря;
- количество объектов;
- суммарное энергопотребление;
- список транспорта для новичков.

После demo запускается обычное интерактивное меню.

Проект использует Java 21.

```bash
mvn clean verify
```

```text
vyshkat.app.Main
```

## Обязательные вопросы

### Какой принцип SOLID применён наиболее явно и где?

Наиболее явно в проекте применён **Single Responsibility Principle (SRP)**.

Ответственности разделены между отдельными классами:

- `vyshkat.park.RentalPark` отвечает за хранение объектов парка;
- `vyshkat.park.RentalParkService` содержит бизнес-сценарии;
- `vyshkat.park.DefaultServiceCenter` содержит правила технического осмотра;
- `vyshkat.app.ConsoleApplication` отвечает за взаимодействие с пользователем;
- `InventoryNumberGenerator` отвечает за выдачу инвентарных номеров.

Например, изменение правил технического осмотра требует изменения
`DefaultServiceCenter`, но не требует изменения `RentalPark` или
`ConsoleApplication`.

### Какой принцип сознательно ограничен и почему это приемлемо?

В проекте сознательно ограничено применение **Open/Closed Principle**.

Для добавления нового вида транспорта не требуется изменять
`RentalPark` или `RentalParkService`: новый класс может наследоваться
от `Transport`, а при необходимости реализовать `EnergyConsumer`.

Однако если новый вид транспорта должен создаваться пользователем через
консольное меню, придётся изменить `ConsoleApplication` и добавить новый
вариант в меню.

Для небольшого консольного приложения это ограничение принято осознанно:
создание дополнительной фабрики и отдельной системы регистрации типов
транспорта усложнило бы проект без необходимости. При этом основная
бизнес-логика от конкретных видов транспорта не зависит.

### Что произойдёт при расширении программы?

#### Новый вид транспорта

Нужно добавить новый класс-наследник `Transport`.
Если транспорт потребляет энергию, он также реализует `EnergyConsumer`.

`RentalPark`, `RentalParkService` и расчёт энергопотребления менять
не потребуется.

Если новый транспорт должен создаваться через консоль, потребуется
добавить соответствующий пункт в `ConsoleApplication`.

#### Сотрудник

Сотрудник не является объектом, находящимся на балансе парка, поэтому
он не должен реализовывать `InventoryItem`.

Для сотрудников можно добавить отдельную модель и отдельное хранилище.
Существующие классы транспорта и оборудования при этом менять
не потребуется.

#### Склад запчастей

Склад запчастей представляет отдельную часть предметной области.
Для него можно добавить сущность запчасти, отдельное хранилище и сервис.

Существующие `Transport`, `Equipment`, `RentalPark` и
`RentalParkService` для этого изменять не требуется.

### Как тестами фиксируются правила и как подменяется зависимость?

Правило технического осмотра проверяется в `DefaultServiceCenterTest`.

В нём отдельно проверяются основные условия:

- неисправные тормоза приводят к отказу;
- слишком плохое состояние шин приводит к отказу;
- недостаточный заряд энергопотребляющего транспорта приводит к отказу;

Правило для новичков фиксируется в `TransportTest`:

- `friendlyForBeginner = 5` — транспорт не подходит новичку;
- `friendlyForBeginner = 6` — транспорт уже подходит новичку.

В `RentalParkServiceTest` настоящий `DefaultServiceCenter` заменяется
на `FakeServiceCenter`, реализующий тот же интерфейс `ServiceCenter`.

Например, в тесте `shouldAddTransportWhenServiceCenterAcceptsIt`
fake возвращает положительный результат осмотра, а тест проверяет,
что транспорт был добавлен в `RentalPark`.

В тесте `shouldNotAddTransportWhenServiceCenterRejectsIt`
fake возвращает отрицательный результат, и проверяется, что транспорт
в парк не попал.

Таким образом `RentalParkService` тестируется независимо от настоящих
правил техосмотра, а зависимость подменяется через constructor injection.

### Как использовался ИИ?

ИИ использовался как вспомогательный инструмент при разработке проекта:

- для ревью кода и поиска возможных проблем;
- для обсуждения вариантов реализации технического осмотра и архитектуры приложения;
- для помощи в оформлении README.

Окончательные решения по структуре проекта, используемым абстракциям,
бизнес-правилам и набору тестов принимались после самостоятельного
разбора предложенных вариантов.
